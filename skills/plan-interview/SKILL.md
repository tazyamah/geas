# 初回の対話で plan を作る

出典：このスキルは、Cockburn が提唱したユースケース手法に基づく。Alistair Cockburn, *Writing Effective Use Cases*, Addison-Wesley, 2000（日本語訳『ユースケース実践ガイド』ウイングス）。

人が最初に話した内容（アプリの望み）から、短い一問一答を繰り返して plan の仕様書（①）を作る。道具は台帳（JSON）で、`python -m geas interview` の `status`（次に聞くこと）と `render`（plan の Markdown）を使う。台帳は plan の元であり、コードから作らない。

## 約束

- **1回に聞くのは1問**。短く。長い一覧を見せて全部答えさせない。
- **AI が決めたことは書かない**。決まっていないことは問い（questions）にする。意図的に決めない場合は status を `unspec`（未規定）にする。「まだ聞いていない」と「決めない」を混ぜない。
- **人に見せる言葉は平素に**。専門用語は括弧の中に回す。例：「動作要件（動作するプラットフォーム）」でなく「動かす環境（動作要件）」「動作するプラットフォーム」でなく「何の上で動かすか（動作するプラットフォーム）」。IT知識がない人でも答えられる聞き方にする。
- 曖昧な答えは具体例で確かめる（「たとえば〜の場合は？」）。番号だけの答えは、どれと受け取ったかを返す。
- 判断（J）は、**AI が解釈したルール1つにつき1件**。人は一問一答にきれいに答えないので、1つの返答から複数の J ができることも、複数の返答で1つの J になることもある。judgments に「ルール・元の発言（複数可）・誰が・いつ」を書く。
- **会話に出ていないものは存在しないものとして扱う**。操作する人以外の関心（利害関係者）を、こちらから掘り起こさない。ただし、新しい要求が**すでにある判断（J）のルールとぶつかる**ときは、「この判断とぶつかるがどうするか」を人に聞く。
- 用語は常に「ユースケース」（Cockburn の手法に基づく）を使い、「目標」「シナリオ」などと言い換えない。
- **少なく強いルールに誘導する**（目標：少ないルールの組み合わせで、仕様のすべてを説明できること）。質問ごとに、すでにある判断（J）や、世の中でよく知られた振る舞い（例：Gmailの送信取り消し）に**そろえる案**を選択肢に入れ、おすすめにして理由を添える。例：「圏外でも書ける（J28）ので、直す・消すも同じ扱いにそろいます」。個別の例外を増やす答えが出たら、「既存のルールにそろえられないか」を先に聞き返す。ルールが増えたら、似たもの同士を1つのルールにまとめられないかを見直す。
- **報告と質問を混ぜない**：結果の報告は普通に書いてよいが、報告のあとに人へ確認したいこと・未解決の問いがあるときは、まとめて並べず、1問だけ聞く（答えをもらってから次の1問）。「確認してほしい整理」「新しい問い」を報告の末尾に列挙しない。
- **質問の形**：選択肢（番号）と自由な答えのどちらでもよい形で、おすすめとその理由を1つ付ける。人の答えの意図（たとえば「電波が悪くて取り消せないのを防ぎたい」）が選択肢の外にあったら、選択肢に収めず、意図を満たすもっと良い方法を提案する（例：消す操作を端末の中で先に確定し、保留後に外へ反映）。
- 作りこみの手順（この聞き方）と、アプリの動作を混ぜない。台帳のユースケースにはアプリの動作だけを書く。

## 進め方（Cockburn の外側から内側へ）

1. **範囲**：作るものの一言（summary）と範囲外（out_of_scope）。範囲外は PMBOK のスコープ記述書の考え方。
2. **アクターとユースケースの一覧**：「誰が、何をしたいか」を1行ずつ。「他に使う人は？ 他にやりたいことは？」で足りないものを聞く。ユースケースの粒度（要約／利用者目標／下位機能）を付ける。利用者目標を基本にする。
3. **ユースケースごとの肉付け**（1ユースケースずつ、ここを繰り返す）：
   1. 主な流れ（成功の道）を3〜9手で。
   2. 失敗・例外・分岐（拡張）：「この手がうまくいかなかったら？」を手ごとに聞く。
   3. ルール（青）→ 具体例（緑）→ 未解決の問い（赤）に分けて聞く。具体例は前提・操作・期待で書く。
   4. 未解決の問いが0（または意図的に未規定）になったら、そのユースケースは終わり。
4. **付加情報の仕分け**：人は1つのユースケースへの返答に、別のユースケース・動作要件・制約・品質（速さなど）を混ぜる。気づいたら extras に書き、`kind`（runtime／constraint／quality／other）で仕分け、元のユースケースには残さない。別のユースケースに当たるものは usecases に足す。
5. **動作要件**（コードを書き始める前）：ユースケースが固まったら `status` が R1〜R7 を示す。溜まった extras を先に見せ、足りないものを1問ずつ聞く。少なくとも **R1（動作プラットフォーム）は確定**させる。R8 以降は今は扱わない（v0.1.0 のあとのフレームワーク側の仕様）。出典は notes/spec-runtime-requirements-checklist.md。
6. **レビュー操作パネル**：画面の下に浮かぶ小さなパネル（操作を選ぶ欄、[最初から][前へ][次へ]、最後に[OK][NG]。NGは理由を書ける。NG済みの操作ではNGボタンが「NG✎」になり、カーソルを重ねる／押すと入力済みの理由が確認・編集できる。理由には、そのときの画面の状態（端末・状況・手順・入力内容）を一緒に保存する。各操作の最初の[前へ]は、一つ前の操作の最後の状態に戻る）で、押す場所を光らせながら1手ずつ進める。ボタン連打だけで、どう操作するかが分かるようにする。強調はUI上にない黄色で太くする。端末ごとに別の操作があればそれも一覧に入れ、全操作のうち何件レビューしたか（すべて完了か）を常に表示する。文字は少なく。ユースケースのIDは図や一覧の隅に小さく薄く書き、目立たせない。
7. **画面の動きを台帳に書く**（screens）：画面ごとに、見せるもの、状態ごとの表示（空・読み込み中・圏外・失敗など）、押したらどうなるか、出来事（開いた・つながった・時間がたった）で起こること、を判断（J）の番号つきで書く。動作要件で画面ありと決まったら、`status` が画面の動きを聞く。出来事は、あとでコードのトリガ（きっかけ）になる。
8. **人に見せるのは図と画面の動き**：文字の羅列は見落としやすい。ユースケース図と、さわれる画面ワイヤーフレーム（スマホとPCの両方。ユースケースを実行する実操作の一覧に「やってみる」と「合っている／違う」を付ける。押したらどうなるか、空・読み込み中・失敗・圏外などの状態の切り替えつき）を作って見せる。各所に判断の番号を付ける。AIの案・解釈の箇所は図の中に明記する。
9. `status` が「コードを書き始めてよい: はい」になったら、`render` で plan を出して人に見せる。レビューを経てからコードに起こす。

## 台帳から plan へ

台帳の render は plan の会話の部分（節 C0〜C5）。plan 雛形の節1〜7（データ・状態と遷移・処理・指定事項・具体例の表）は、**コードより前に**、この内容から会話で書き起こして人に見せる。コードから表を起こさない（突合の独立性が崩れる）。付加情報の仕分け（kind）は AI が決めず、人に確かめる。節1〜7を書いたら、人が判断するべき点（未解決の問い）も**まとめて見せず、1問ずつ**聞く。人に「とりあえず作って」と言われても、R1（動作プラットフォーム）だけは聞く。動作要件は status を `open`／`unspec`／`answered` で持ち、R1 は `unspec` にできない。

## 台帳の書き方

`interview init 台帳.json --title 題名` で作る。形は geas/interview.py の冒頭を見る。JSON は Edit で直接直してよい。書いたら必ず `status` を実行し、次に聞くことを確かめる。
