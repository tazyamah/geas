# 生成したサーバーの動かし方

`geas rust --host --runtime` で出る `server/` は、手元で動かすための小さなサーバーです。インターネットに直接さらすためのものではありません。公開するときは、nginx などの Web サーバー（リバースプロキシ）を前に置きます。geas の機能だけで公開の要件を満たす予定はありません。

## 起動の引数

`geas_server [--port 8787] [--host 127.0.0.1] [--workers 4] [--db app.sqlite] [--pwa ../ui] [--test [--dev ../dev]] [--allow-host 名前] [--seed 別の最初のデータ.json] [--secrets シークレット.json]`

- `--host`：待ち受けるアドレス。既定は `127.0.0.1`（同じ機械からだけ）。プロキシを前に置くなら、既定のままにして、プロキシだけが届くようにします。
- `--workers`：リクエストを処理するスレッドの数（1〜256、既定 4）。
- `--test`：テストと開発のための口を開きます（下の「外から呼べる口」）。生成した通しテストは、これを付けて起こします。公開するサーバーには付けません。
- `--dev`：開発用の模擬操作パネルのフォルダ。`--test` のときだけ配ります。
- `--secrets`：外部作用（`over http`）の認証に使う値のファイル（`{"外部.名前": "値"}`）。環境変数 `GEAS_SECRET_外部_名前`（大文字）が優先。値は仕様書にもログにも出しません。
- `--effect-url 外部.操作=URL`：（`--test` のときだけ）宣言した通信先を、試験用の URL に替えます。`--test` なしで付けると起動を断ります。
- `--allow-host`：`localhost` と IP の書き方（`127.0.0.1`・`[::1]`・`192.168.0.5` など）のほかに、Host として受ける名前。何度でも書けて、カンマ区切りでもかまいません。名前で書いた `--host` も受けます。ほかの名前の要求は 403 で断ります（下の「守られること」）。
- `--seed`：生成物に埋め込んだ最初のデータの代わりに使う JSON（`{"実体名": {"キー": {行}}}`）。最初のデータは、埋め込みも `--seed` も、DB が空のときだけ読んで入れます。行のある DB で起こすときは読まないので、起動の時間とメモリは最初のデータの大きさによりません。

## 外から呼べる口

`--test` を付けないとき、サーバーが答えるのは次のものだけです。

- 仕様書の URL の表で「外から」が「呼べる」の口（`resource` の宣言から作った RESTful な URL）。画面の URL は、ブラウザで開くと画面の殻（HTML）を返します。
- 画面のファイル（`--pwa` のフォルダ）、`/manifest.webmanifest`、画面が使う定義 `/api/defs`（画面と、外から呼べる URL だけ。定義の全部は `--test` のときだけ）と、生きているかの確認 `/api/health`（DB に届かなければ 503）。
- 入力の誤りは 400 で理由を返します。サーバーの中の失敗（DB など）は 500 で、理由は標準エラーのログ（`geas.error`）だけに出します。
- `.geas` の実体の項目を変えたあとに、前の版で作った DB で起こすと、起動のときに理由を言って止まります項目を足す・名前を変える・消すときは、`.geas` の `migration` に書いておけば、起動時に前の版の DB を今の形へ書き換えます（[language-reference.md](language-reference.md) の「保存の形の移行」）。

`--test` を付けると、次のものも開きます。どれも、仕様書の URL の表を通らずに、どの処理・問い合わせでも名前で呼べたり、時計や模擬の返事を変えて全員の注文に効かせたりできるためです。

- 仕様書の URL の表で「内部（流れの途中）」の口：返事・期限・前の処理の結果から進む処理を呼ぶもの（注文の確定・決済の見立てなど）。外から呼べると、決済の返事などの確かめを飛ばして先へ進められます。付けないときは 404 です。流れの中で呼ぶぶんには、どちらでも動きます。
- `/api/test/…`：時計を進める、模擬の返事の設定、返事待ちと外部作用の記録。
- `/api/deeds/{処理}`・`/api/queries/{問い合わせ}`・`/api/events/{出来事}`：宣言を通らない、名前での呼び出し。
- 開発用の模擬操作パネル（`--dev` のフォルダ、`/test.html`）。

## ログ

REST の経路を 1 つ処理するたびに、標準エラーに 1 行の JSON を出します（`"log":"geas.route"`、動作・経路・呼んだ処理・結果の種類・HTTP の状態・かかった ms）。本文と入力の値は載せません。`python -m geas trace アプリ.geas ログ` が、この行を仕様書のルート表の行に結び、仕様書にない経路・結果・状態を「結べなかったもの」として示します。

## 守られること

- 本文は 16 MiB まで（超えると 413）。JSON の入れ子は 64 段まで。長さを書かない文字列は 1,048,576 文字まで。
- Web からの入力は選別（宣言した項目だけを通す入力の選別）で最初に切り落とされます。上限を緩めた分は、書いた人の責任です。
- 1 リクエスト 1 トランザクションで、直列にする役目は DB が持ちます（`storage … isolation …`）。
- POST は `Content-Type: application/json` のものだけを受けます（ほかは 415）。別のサイトのページは、フォームや `text/plain` の POST なら事前の確認なしに送らせられますが、JSON と名乗る要求はブラウザの事前確認（CORS）で止まります。サーバーは CORS を開けていないので、別のサイトからは届きません（CSRF の対策）。
- 本文は UTF-8 で読みます（そうでなければ 400）。パスの `+` は空白にせず、`%` のあとが 16 進の 2 桁でなければ、そのまま残します。
- どの応答にも、CSP（インラインのスクリプトを動かさない）・`X-Content-Type-Options: nosniff`・`Referrer-Policy: same-origin` を付けます。
- Host が `localhost`・`*.localhost`・IP の書き方・`--allow-host` の名前のどれでもない要求は、読むのも書くのも 403 で断ります。ブラウザで開いた悪意のあるページが、DNS の付け替え（DNS rebinding）で `127.0.0.1` のサーバーに同じオリジンとして届いても、ブラウザは Host にそのページの名前を書くためです。
- 期限と返事の処理は、待ち 1 件ずつ進めます。1 件が失敗しても、標準エラーに 1 行（`"log":"geas.tick"`、失敗した待ち・種類・理由）を残して、ほかの待ちは止めません。

## 守られないこと（前に置くものに任せる）

- **遅い送信**：本文をゆっくり送る相手は、その間 worker を 1 つ占めます。HTTP サーバー部品（tiny_http）には、読み込みの時間切れを設定する口がないため、サーバー自身では切れません。nginx は本文を受け終えてから中継するので、`client_body_timeout`・`client_header_timeout`・`client_max_body_size` を設定してください。
- **呼べる人の区別（認証・権限）**：ありません。サーバーに届く人は、仕様書の URL の表にある口をすべて呼べます（客の操作も、お店の側の操作も）。公開するときは、プロキシの認証の入口で、届く人を絞ってください。
- **接続数・レート制限・TLS・認証の入口**：`limit_conn`・`limit_req`・証明書などをプロキシ側で設定します。
- **複数台**：同じ DB ファイルを使う限り、サーバーを複数台動かしても直列は保たれます（試験あり）。期限の発火も、待ち 1 件につき 1 回だけです（待ちを消せた 1 台だけが進む。試験あり）。

## nginx の例

```
location / {
    proxy_pass http://127.0.0.1:8787;
    client_max_body_size 16m;
    client_body_timeout 10s;
    client_header_timeout 10s;
}
```

この例では、nginx がサーバーへ送る Host は `127.0.0.1:8787` なので、`--allow-host` は要りません。`proxy_set_header Host $host;` で公開の名前を渡すなら、その名前を `--allow-host` に書きます。

## 保存とメモリ

- サーバーは保存（全部の entity の行）をメモリに持ち、処理と問い合わせはその上で動きます。DB へは、処理が変えた行だけを書きます。1 リクエストごとに保存の全件を読み直すことはありません（お店アプリで各 1 万件、計 3 万行のとき、注文 1 件が約 0.4 ミリ秒）。
- メモリは保存の件数に比例します（上の 3 万行で約 30MB）。起動したときは読まず、最初のリクエストで全部を読みます。
- 同じ DB ファイルを別のサーバーや道具（`sqlite3` など）が書き換えたことは、次のリクエストの最初に SQLite の `data_version` で分かり、そのときは全部を読み直します。複数台で同じ DB を書き合うと、そのたびに読み直すので、1 台のときより遅くなります。
- 処理が途中で失敗してトランザクションを巻き戻したときは、メモリ上の保存も捨てて、次のリクエストで読み直します。

## 問い合わせの版（ETag）

- 問い合わせの URL（`index`・`show`）の応答には、答えの版（`ETag`）を付けます。版は、メモリ上の保存の世代（処理が行を書くか、DB から読み直すたびに変わる）と、起動ごとの値と、URL から作ります。問い合わせは保存と入力だけで決まる（時計を使わない）ので、同じ URL で版が同じなら、答えも同じです。
- 要求の `If-None-Match` が今の版と同じなら、問い合わせを実行せずに `304`（本文なし）を返します。別の接続の書き込みは、その前に `data_version` で確かめます。再起動したあとは、前の版では `304` になりません（止まっている間に DB が書き換えられても、古い一覧を使わせない）。
- 生成した画面は、見せている一覧を 2 秒ごとに引き直すときに、前の版を送ります。`304` なら、覚えている行を使い、描き直しません（お店アプリで商品が 1 万件のとき、一覧を開いて何もしていない 10 秒の間に、ブラウザが働いていた時間が 8.6 秒から 0.01 秒に、送った量が 5.4MB から 0 になりました）。
- 答えが変わったときも、前に描いた行と HTML が同じ行は残し、変わった所だけを作り直します。選ぶ欄の選択肢も、前と同じなら作り直しません（お店アプリで商品が 1 万件のとき、商品の管理の画面で入荷を押してから描き終わるまでが 481 ms から 206 ms になりました）。
- `304` を返したときも、ログの行は出します（状態は `304`、結果の種類はなし）。
- 行のある問い合わせの答え（`{"rows":[…]}`）は、生成した処理が行を 1 本の文字列に続けて書いた JSON を、サーバーで解析し直さずにそのまま本文にします。行の項目は `select` に書いた順に並びます（お店アプリで商品が 1 万件のとき、一覧の応答が 46.6 ms から 5.8 ms に、10 万件で 478 ms から 65 ms になりました）。
