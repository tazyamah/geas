# 仕様書とコードがずれない仕組み：geas の考え方と、信頼してよい範囲

このファイルは、人が geas を信頼してよいかを判断するための解説です。「何がどう保証されているか」だけでなく、**まだ保証されていないこと**も書きます。主張は、リポジトリの実装とテストを根拠にしています（根拠の場所を各節に添えました）。AI 向けの入口は [ai-guide.md](ai-guide.md) です。

## 1. 基本の考え

geas の狙いは、**AI がコードを書き、人はコードを一切読まずにレビューできる**ことです。そのために、仕様書とコードを「あとで見比べる別々のもの」にせず、**同じ正本から機械で作る**ようにしています。守らせる相手は、アプリの利用者ではなく、geas で作る人（と AI）です。制約を重くするほど、保証が強くなります（名前の由来の「誓い」はここから来ています）。

人が読むのは、`.geas` ではなく、そこから生成した仕様書（`geas spec` の Markdown、`geas review` のスマホ幅 HTML）です。人が確かめるのは、仕様書を頭から最後まで読んで「これで合っている」と言えるかどうかです。

## 2. ずれない仕組みの骨組み

```
会話 → 計画書（任意の突合用）
            │
        .geas（正本）── 検査器 check ──┬─ 仕様書（spec / review）
                          │            └─ Rust（rust）→ 画面・拡張・サーバー・MCP
                       通らなければ、ここで止まる
```

### 2.1 仕様書とコードは、同じ検査結果から作る

仕様書もコードも、`.geas` を一度だけ解析・検査した結果（`Checker`）から出ます。

- 仕様書：`spec.build(ck)` が検査結果から構造を取り出す（`geas/spec.py`）。人向けの表示は `review.py`・`svg.py`。
- コード：`rustgen.generate(ck)`（`geas/rustgen.py`）。

どちらも `cli.py` で同じ `ck` を受け取ります。仕様書の「読む・書く・遷移・外部作用・物理型」の欄は、コードを生成するときに使う情報そのものです。たとえば `tests/test_geas.py` の「仕様書は読み書きと遷移をコードから取り出す」「物理数は範囲から選ばれる」は、仕様書に出た内容（書く項目、`u64` などの実現型）が検査結果と一致することを確かめています。

つまり「仕様書は正しいが、コードは別のことをしている」という形のずれが、構造として起きにくくなっています。

### 2.2 仕様書に現れない手書きコードを置かない

生成物は、画面（PWA）、ブラウザ拡張、開発用パネル、サーバーの実行部（SQLite と HTTP）、MCP のツール定義、通しテストまで、すべて `.geas` と計画書から作ります。生成ファイルの先頭には「自動生成。手で編集しない」と入り、`servergen.py`・`extgen.py`・`screengen.py`・`mcp.py` の説明にも「手で書くコードは無い」とあります。サーバーの実行部はアプリを知らず、生成した定義（`DEFS_JSON`）だけで動きます。

例外は、**外から足す部品（`part`）の実装**です。これはアプリが書く `trait Parts` で、geas の外にあります。だから部品には、宣言した保証（`guarantee`）を持たせ、呼ぶたびに戻り値の範囲と保証を実行時に確かめます（違反したら書き込む前に処理を止めます。`rustgen.py` の `guarantee_violated`）。保証が無い部品は検査でエラーです。

### 2.3 通らないものは先へ進ませない

`geas check` はエラーと「問い」（QUESTION）を出します。問いは「人に聞くべきことを、検査器が『決めていない』と見つけたもの」です（丸めの方向、存在しない場合の扱い、削除の扱いなど）。エラーか問いが残っていると、`rust` と `compare` は先へ進みません（`cli.py` の `ck.ready` の判定）。AI が黙って決めて進めることを、仕組みで止めています。エラーのあるコードからは Rust を生成しないことも、テストで確かめています（`test_エラーのあるコードからは生成しない`）。

### 2.4 「書けない書き方」を増やして保証にする

geas では、守れると示せない書き方は、そもそも書けません。主なものは次のとおりです（検査器は `geas/check.py`）。

| 約束 | 検査器の動き | 止まる例のテスト |
|---|---|---|
| 不変条件（在庫が 0 を下回らない、など） | 項目へ書くたびに、その場で値の範囲から守れると示す。示せなければエラー。「証明済み」かどうかが仕様書に出る | `test_在庫不足の判定を削ると不変条件が示せない`、`test_項目の更新で在庫を減らすと範囲も不変条件も示せない` |
| 状態の遷移 | 宣言した順にしか進まない。元の状態を確かめずに変えるとエラー | `test_宣言に無い遷移は止まる`、`test_元の状態の確認が無いと止まる` |
| 無い・null | 無いかもしれない値は、確かめてからでないと使えない | `test_存在を確かめない参照は問いになる` |
| 金額と整数 | 型が違うので混ぜられない。端数が出る計算は丸めの指定が要る | `test_丸めの指定が無いと問いになる` |
| 外部作用 | 冪等キーが必須 | `test_冪等キーが無いと止まる` |
| 並列（`par`） | 枝が同じ項目へ書く・読み書きが重なると、順序が結果に効くのでエラー | `test_par_の枝は…` |
| 値の範囲 | 項目の型より広い値は書けない。物理型（`u8`・`u64` など）は範囲から選び、リリースビルドでも `overflow-checks = true` | `test_物理数は範囲から選ばれる` |

### 2.5 外から入る値は境界で毎回確かめる

内部の値は型と検査器で守り、**外部（人・他システム）から入る値だけ**を、入口で実行時に確かめます（長さ・文字種・範囲・`check gtin`・時刻の範囲など）。宣言にない項目は「来ていないもの」として扱います。根拠は `test_geas.py` の「ホストは入力の長さと文字を境界で確かめる」「slot も境界で宣言の範囲を確かめる」、お店の通し `test_外から来る値は境界で確かめる` です。

### 2.6 動かして確かめる

「検査を通った」だけで済ませず、生成した Rust を実際に動かします。

- **言語機能ごとの動作テスト**：[language-test-map.md](language-test-map.md) に、リファレンスの項目ごとに、生成物を動かして確かめるテストがあるかを一覧にしています（◎ 動かして確認／○ 静的に止めるのみ／✕ まだ無い）。機能を足したら表に行を足します。
- **決定性**：同じ `.geas` からは同じ Rust が出ます。コミットした生成物と一致することをテストで確かめます（`test_生成は決定的で_コミットした生成物と一致する`）。
- **お店アプリの通し**：決済・倉庫の返事待ち、期限切れ、再起動後の復元、冪等キーでの再請求などを、サーバーまで組んで動かします（`tests/test_shop_app.py`、`tests/test_runtime.py`）。
- **計画書の具体例**：計画書（会話で作った仕様書）の表の「具体例」「URL の具体例」「画面の具体例」から、HTTP の通しテストと、実ブラウザ（Playwright）の画面テストを**生成**します（`testgen.py`）。期待値は計画書側にあり、コードから独立しています。テストは手で書かず、直すときは計画書の表を直します。

### 2.7 計画書との突合（任意の追加の網）

`geas compare` は、計画書の◆欄とコードから生成した仕様書を突き合わせ、「計画にあってコードにない」「コードにあって計画にない」「値が違う」「具体例の不一致」「未規定」を出します（`plan.py`）。2026-10-29 の決定で、これは**必須の関門ではなく任意の検査**です。人がレビューする対象は、どの流れでも「生成した仕様書の全体」で変わらないからです。ただし、計画書の具体例からのテスト生成は、コードから独立した期待値として残します。

更新のときは、前の版（git の前のコミットなど）から生成した仕様書と比べて差分を出せます（`geas review --diff-o … --base-git HEAD~1`）。

## 3. 信頼してよい範囲と、まだ保証していない範囲

ここが正直な部分です。**geas は数学的な証明を、まだコード全体には与えていません。** 保証には強さの違いがあります。

| 層 | いまの保証 | 強さ |
|---|---|---|
| Rust 自体のメモリ安全・型安全 | rustc が保証する（生成物の大半は安全な Rust） | コンパイラによる |
| 検査器が静的に示すこと | 不変条件、値の範囲、null でないこと、存在の確認、遷移の順、par の重なり | 検査器の実装が正しい限り |
| 外から入る値・部品の戻り値 | 実行時に毎回確かめる | 実行時の検査 |
| 生成物が `.geas` どおり動くこと | 言語機能ごとの動作テスト、通しテスト | テスト（例による確認） |
| 仕様書が `.geas` を正しく表すこと | 同じ検査結果から作る（2.1） | 構造による。表示の描画は別 |

主な穴は次のとおりです。

1. **検査器の健全性は証明されていません。** 検査器が「示せた」と判断した所の一部は、実行時の確認を省く前提になります。ただし、**生成するRustは、panic も未定義動作も起こしうる構文を使わない**ように束縛しています（`unsafe`・`unwrap`・`expect`・添字・素の算術を使わず、`#![deny(unsafe_code, clippy::unwrap_used, …)]` を生成物の先頭に置いて、`cargo clippy` で強制します）。書込先や null でない値の取り出し、物理型への変換、計算のあふれは、無ければ `Fault` を返します。このため、検査器に抜けがあっても、起きるのは panic やメモリ破壊ではなく、`Fault` として見つかる異常です。処理は純粋な関数なので、`Fault` のときは書込が適用されず、保存は変わりません。テストは `tests/test_geas.py` の「生成した処理は clippy の panic 禁止を通り、禁止を破ると落ちる」です。残る穴は、`Fault` が実際に起きないこと（＝検査器が示したこと）が、まだテストの例でしか確かめられていない点です。
2. **言語機能ごとの動作テストに ✕ が残っています**（[language-test-map.md](language-test-map.md) の末尾）：`event … external → 処理`、サーバーへの同時書き込みの直列化、`now`・`tz_offset` を使う処理、MCP を実サーバーに中継した確認。
3. **画面デザインの詳細と、仕様書の描画（図・配色）**は、「ずれがない」保証の対象ではなく、人の目で確かめる部分です。
4. **部品（`part`）の実装**は geas の外にあり、保証は実行時の確認です。
5. テストは例による確認で、全入力についての証明ではありません。
6. **（解消済み）金額の上限が物理型に収まる証明が無かった穴。** お店の例で、単価が `i64` の最大値・数量が 2 のとき `place_order` が `物理数に収まらない` で panic しました（2026-10-29 に確認）。いまは、整数と金額の範囲を物理型に収まる範囲として扱い、項目へ書く値が収まると示せなければ検査でエラーにします。合計は写像の `max N`（要素数の上限）と `ltype` の上限から示し、加算は上限の確認（`if x.n > 995 { return Full }`）から示します。テストは `tests/test_geas.py` の「合計が収まると示せなければ止まる…」「加算は上限の確認が無いと止まり…」など。

## 4. 「証明できる」へ近づける方向（案）

保証を強くする道筋として、次が考えられます。どれも現状には入っていません。

- 【実装済み】生成規則の束縛：生成物から panic できる構文をなくし、clippy の指定で強制する。残る課題は、`Fault` が起きないことの機械的な証明（Kani など）です。
- 生成した Rust に対して Kani（モデル検査）や Creusot・Prusti（契約検証）のような道具を当て、不変条件や `unwrap_unchecked` の前提を機械で示す。証明の対象は「生成器が出す定型のコード」に絞れるので、アプリごとに手で証明する必要はない見込み。
- 検査器の核（範囲の計算・存在の追跡）を小さく切り出して、独立に検証する。

Kani は、この環境にも導入できて動くことを確かめました（kani-verifier 0.68）。ただし、`place_order` の「どんな在庫・入力でも panic しない」を `BTreeMap<String, …>` のまま検証させる試作は、展開の上限を 6 にしても 7 分以内に結論が出ませんでした。標準の `BTreeMap` と `String` は、モデル検査に重いためです。実用にするには、検証用ビルドでだけ小さな固定容量の表と文字列に差し替える生成が要ります。

どれを採るかは、効果と手間の見極めが要るので、別の PR で扱います。

## 5. まとめ

- 仕様書とコードは、同じ検査結果から機械で作る。手書きのコードを置かない。
- 守れると示せない書き方は書けない。エラーと問いが残る間は先へ進まない。
- 外から入る値は境界で毎回確かめ、生成物は実際に動かして確かめる。
- ただし、検査器自身の正しさと、`unsafe` を使う箇所の根拠は、いまはテストで支えている段階で、数学的な証明ではない。
