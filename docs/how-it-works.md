# 仕組み：なぜ仕様書とコードがずれないのか

geas の狙いは、**AI がコードを書き、人はコードを一切読まずに、仕様書だけでレビューできる**ことです。そのために、仕様書とコードを「あとで見比べる別々のもの」にせず、**同じ正本（`.geas`）から機械で作ります。** この文書は全体のつかみです。根拠のテストと、まだ保証していないことの全部は [why-spec-and-code-dont-drift.md](why-spec-and-code-dont-drift.md) にあります。

## 全体の形

```
会話 → 計画書（任意の突合用）
            │
        .geas（正本）── 検査器 check ──┬─ 仕様書（review / spec）
                          │            └─ Rust（rust）→ 画面・拡張・サーバー・MCP
                       通らなければ、ここで止まる
```

仕様書もコードも、`.geas` を一度だけ解析・検査した同じ結果から作ります。仕様書の「読む・書く・遷移・外部作用」の欄は、コードを生成するときに使う情報そのものです。だから、「仕様書は正しいが、コードは別のことをしている」という形のずれが、構造として起きません。

## 4 つの仕掛け

### 1. 書けない書き方を増やす

守れると示せない書き方は、そもそも書けません。検査器が、コードを書いた時点で止めます。

| 約束 | 検査器の動き |
|---|---|
| 不変条件（在庫が 0 を下回らない、など） | 項目へ書くたびに、値の範囲から守れると示す。示せなければエラー |
| 状態の遷移 | 宣言した順にしか進まない。元の状態を確かめずに変えるとエラー |
| 無い・null | 無いかもしれない値は、確かめてからでないと使えない |
| 金額と整数 | 型が違うので混ぜられない。端数が出る計算は丸めの指定が要る |
| 外部作用 | 冪等キーが必須 |
| 値の範囲 | 計算の途中も、型の範囲に収まると示せなければエラー |

### 2. 外から入る値は、入口で毎回確かめる

内部の値は型と検査器で守り、外部（人・他システム）から入る値だけを、入口で実行時に確かめます。長さ・文字種・範囲・検査数字・時刻の範囲などです。

### 3. 仕様書に出ない手書きコードを置かない

画面、ブラウザ拡張、サーバーの実行部、MCP のツール定義、通しテストまで、すべて `.geas` と計画書から生成します。例外は、根の言語のライブラリを呼ぶ部品（`library`）だけで、呼ぶ先も確認の段階も、仕様書の「人の保証」に出ます。

### 4. コードがすることは、全部仕様書に出す

「ずれない」だけでは、コードを読まないレビューは成り立ちません。仕様書に出ない動きがあれば、そこを変えても人は気づけないからです。処理の中身（どの条件でどの結果になるか）まで仕様書に出し、出し忘れていないかをテストで測っています。

## 動かして確かめる

「検査を通った」で済ませず、生成した Rust を実際に動かします。言語機能ごとに動作テストがあり（[対応表](language-test-map.md)）、計画書の具体例から HTTP の通しテストと実ブラウザの画面テストを生成して、期待値をコードから独立させています。更新のときは、前の版との差分だけが人に出ます。

## どこまで信頼してよいか

| 層 | いまの保証 |
|---|---|
| Rust 自体のメモリ安全・型安全 | rustc が保証する。生成物は panic や未定義動作につながる構文を使わない |
| 検査器が静的に示すこと | 不変条件、値の範囲、null でないこと、遷移の順、並列の重なり |
| 外から入る値・部品の戻り値 | 実行時に毎回確かめる |
| 生成物が `.geas` どおり動くこと | 動作テストと通しテスト（例による確認） |

**geas は、数学的な証明を、まだコード全体には与えていません。** 検査器の健全性の証明、`library` の中身、画面デザインの詳細などは、保証の対象外か弱い部分で、何が弱いかも仕様書の「保証の強さ」の表に出ます。全部の穴は [why-spec-and-code-dont-drift.md](why-spec-and-code-dont-drift.md) の 3 節にあります。
