# モジュール（ファイルの分割と再利用）の設計（2026-10-27）

状態: 設計のみ（未実装）。tazyamah との議論で決まった方針をまとめる。

## 目的と単位

- よく使う定義を、再利用できる単位にする。単位は**業務に特化しない共通概念**（論理日付、標準の論理型・変換・部品、など）。
- 業務の単位（注文など）はモジュールにしない。注文の取り消しには、決済のように作者が知りえない要件が入るので、持ち主が公開する処理だけでは足りない。
- 読みやすさのための分割は要らない（Geas のコードは人が読まない）。ファイルが巨大になって悪影響が出るなら、そのとき別に考える。
- 将来、モジュールを先に検査・コンパイルしておき、その結果だけを取り込めるようにする（検査を軽くする）。
- 「伝票風に管理されるデータ」のように、アプリごとに部品の型が違う概念は、固定の entity では足りず、型を渡す形（パラメータつき）が要りそう。別の論点として後に回す。

## 型の規則（モジュールの境界でも守る）

- 比較・四則・代入ができるのは組み込み型だけ。論理型は「組み込み型 + 制約」で、演算は元の組み込み型で行う（暗黙の変換。物理は同じで、制約は検査器が見るだけなので、実行時の費用はない）。合成型は成分に分けて組み込み型として読む。
- したがって、モジュールの境界を越えるのは「元の組み込み型 + 制約（範囲など）」だけ。物理型は越えない。

## 約束（言語が守らせること）

1. **entity を書けるのは、その entity を定義したモジュールの処理（deed）だけ。** 外のモジュールは、公開された処理を呼ぶか、公開された項目を読むだけ。
2. 取り込まれたモジュールが見えるのは、呼び出し側から渡された値（入力）と参照（slot）だけ。呼び出し側の entity は知らず、書けない。
3. モジュールは循環して取り込めない。
4. 名前は、モジュールごとの名前空間に置く。他のモジュールの名前は `Module.Name` で指す。
5. モジュールをまたぐ不変条件は、最初は書けない。式は書けても、その条件を守る責任がどちらの持ち主にもなく、証明できない。

## 公開するもの（ヘッダーに当たる部分）

- 型の元の組み込み型と制約、処理の入力と結果の種類、問い合わせ、公開すると書いた項目（読み取り専用）。
- 隠すもの: 物理型、保存の形、処理の中身。物理型はモジュールが責任を持って決め、外は口を出さない。外が知るのは「元の組み込み型は何か、何に変換できるか」だけ。
- 公開は、既定は非公開で、書いたものだけを公開する。

## 段階

1. **状態を持たないモジュールから、ソースのまま取り込む。** 論理型・変換・部品。ファイルを取り込んで全体を1つのプログラムにして検査・生成する。名前空間を入れる。仕様書に定義したモジュールの欄を足す。
2. 状態を持つモジュール（entity と処理を持つ）。「書けるのは持ち主だけ」の検査を入れる。
3. インターフェースの出力と取り込み。検査器がモジュールの検査結果から、公開するもの（上記）と、証明できた約束、結果の範囲を出す。使う側は、ソースの代わりにこれを取り込み、自分のコードだけを検査する。生成する Rust は、モジュールごとの crate にできる。モジュールをまたぐ最適化はしない。呼び出しの費用は、小さい関数に `#[inline]` を付けて Rust に任せる。
4. パラメータつきのモジュール（伝票風など）。

## 信頼（検査した結果を使うとき）

- インターフェースには、ソースの内容のハッシュ（SHA-256）、モジュールの version、検査器の version を持たせる。取り込むときに照合し、合わなければエラー。
- インターフェースは、人が手で書く宣言ではなく、検査器が出す（宣言は本物の約束、の原則）。

## 未決（実装しながら決める）

- 取り込みの書き方（`use "path"` と `Module.Name` の形）、公開の書き方。
- 標準のモジュール（仮想日時から実在日時への変換など）の置き場所。
- 同じモジュールを2か所から取り込んだときの扱い（同じ実体にする）。
- 表示名（`///`）の衝突は、モジュールごとに見る。
