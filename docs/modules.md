# モジュール（ファイルの分割と再利用）の設計（2026-10-27）

状態: 設計のみ（未実装）。tazyamah の方針は「B：名前空間つきのモジュール。持ち主のモジュールだけが entity を書ける。まずソースのまま取り込める形から」。

## 目的

- アプリが大きくなったとき、AI が一度に読んで書き直す範囲を小さくする。
- よく使う定義（日付の変換、標準の論理型・部品）を、再利用できる単位にする。
- 将来、モジュールを先に検査・コンパイルしておき、その結果だけを取り込めるようにする（検査を軽くする）。

## 約束（言語が守らせること）

1. **entity を書けるのは、その entity を定義したモジュールの処理（deed）だけ。** 外のモジュールは、公開された処理を呼ぶ（結果を受け取る）か、公開された問い合わせで読むだけで、書き換えられない。
2. 取り込まれたモジュールが見えるのは、呼び出し側から渡された値（入力）と参照（slot）だけ。呼び出し側の entity は知らず、書けない。
3. モジュールは循環して取り込めない。
4. 名前は、モジュールごとの名前空間に置く。他のモジュールの名前は `Module.Name` で指す。名前の重複はモジュールの中でだけエラー。
5. モジュールをまたぐ不変条件は、最初は書けない。

この約束で、不変条件の証明がモジュールの中で閉じる。だから、別々に検査した結果を信用できる。

## 取り込まれるものの種類

- 状態を持たないモジュール（論理型・変換・部品だけ）: 値を受け取って返すだけ。
- 状態を持つモジュール（entity と処理を持つ）: 自分の entity を自分の処理で書く。外に及ぶのは、処理の結果と、公開した問い合わせで読める状態だけ。

## 段階

1. ソースのまま取り込める形。ファイルを取り込んで全体を1つのプログラムにして検査・生成する。名前空間と「書けるのは持ち主だけ」の検査を入れる。仕様書に、定義したモジュールの欄を足す。
2. インターフェースの出力。検査器がモジュールの検査結果から、公開する型・entity の読める項目・処理（入力、結果の種類、読む・書く・遷移・外部作用）・証明できた約束・物理の表現を出す。仕様書の構造化データが、ほぼそのままインターフェースになる。人が手で書く宣言ではなく、検査器が出す。使う側は、ソースの代わりにこれを取り込み、自分のコードだけを検査する。生成する Rust は、モジュールごとの crate にできる。

## 欠点と備え

- モジュールをまたぐ不変条件は、モジュール単位では証明できない。組み立てる側で、インターフェースだけを見て確かめる段階が要る（最初は書けないことにする）。
- 持ち主が公開していない操作は、外から実現できない。使い方を先に考える必要がある。
- インターフェースが古い、または書き換えられると約束が崩れる。ソースのハッシュなどで照合する。
- モジュールをまたぐ最適化が効きにくい。変換の式は、本体までインターフェースに入れて、使う側に展開できるようにする。
- 物理の表現（数のバイト幅など）は、モジュールを検査した時点で決まる。インターフェースに入れる。
- 保存の形を変えやすくするため、外からの読み取りは公開した問い合わせだけにする。

## 未決（実装しながら決める）

- 取り込みの書き方（`use "path"` と `Module.Name` の形）。
- 標準のモジュール（仮想日時から実在日時への変換など）の置き場所。
- 同じモジュールを2か所から取り込んだときの扱い（同じ実体にする）。
- 表示名（`///`）の衝突は、モジュールごとに見る。
