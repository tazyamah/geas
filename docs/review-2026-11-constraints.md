# 制約と部品のレビュー（2026-11-10）

geas の「制約」の部分（検査器が示す範囲・null・遷移・書き込み、`trust` の段階、`library` と標準部品）を、小さな `.geas` を書いて検査器に通す形で確かめた記録。全体の改善点は [review-2026-11.md](review-2026-11.md)、未着手の一覧は [roadmap.md](roadmap.md) にあり、ここには重ねて書いていない。人が読むメモで、強制力は無い。

**どれも動かして確かめた。** 「通ってはいけないものが通る」例は、直したうえで `tests/test_numbers.py`・`tests/test_parts.py` に試験として残した。

## 1. 見つけて直したもの

### 1-1（高）`let` の付け直しで、範囲の証明が崩れていた

```
if m > 5 { return Bad }
if m < 0 { return Bad }
let m = it.total        // -200..200 の値で付け直す
it.total = m * 40       // 検査は「0..200 に収まる」と示したことにしていた（実際は -8000..8000）
```

前の `m` について確かめた範囲（0〜5）が、付け直した `m` に残っていた。検査が「示せた」とした書き込みは、生成物が確かめずに物理数へ移す（`as`）ので、範囲の外の値が黙って保存される。

直し方：`let` で、すでにある名前（入力・slot・前の `let`）は付け直せない（エラー）。パーサが `let mut` を断るときの案内（「let の変数は作り直さず」）と同じ向き。Rust の shadowing を知っている AI が書いても、名前を変える案内つきで止まる。お店アプリなどの見本に、付け直しを使っている所は無かった。

### 1-2（中）数を中身に持つ結果は、検査を通っても生成した Rust が組めなかった

`result Res { Done(left: Qty) }` に `return Done(it.stock)` と書くと、検査は通るのに、生成物は `i128` を `u8` の場所へ渡して組めなかった（見本の結果の中身は ID だけだったので、表に出ていなかった）。範囲も確かめていなかった。

直し方：結果の中身が整数・金額のとき、型の範囲に収まると検査が示す（示せなければエラー）。生成物は、示した値を物理数へ移す。

### 1-3（中）標準部品 277 個のうち 29 個が、安定版の Rust で組めなかった

`geas/std/num.geas` は nightly の rustdoc から作るので、安定版にまだ無い関数（`widening_mul`・`carryless_mul`・`clamp_magnitude`・`deposit_bits`・`extract_bits`・`saturating_cast_signed`・`saturating_cast_unsigned`・`is_utf16_surrogate`・`widening_carryless_mul`・`wrapping_next_power_of_two`）が混ざっていた。呼ぶと、検査は通るのに生成物が組めない。Rust 1.97.0 で確かめた。

直し方：下の 2 の仕組みで見つけ、外した（残り 248 個）。生成器（`python -m geas.stdgen`）も、書き出す前に組んで確かめ、組めないものを外す。

### 1-4（低）確かめた範囲が、`or`・`not` をまたぐと使えなかった

`if m > 5 or m < 0 { return Bad }` の後ろで、`m` が 0〜5 と分からず、`if` を 2 つに分けて書く必要があった（健全だが、不便）。条件の式 `if m > 99 then 99 else m` も、範囲が狭まらなかった。直した（[language-reference.md](language-reference.md) の 4）。

## 2. 部品の信頼性を上げる仕組み：境界値の検査（`geas parts`）

`library` は「人の保証」で、検査器は宣言（引数と戻り値の範囲・`guarantee`・panic しないという理由の文章）を信じて証明に使う。宣言が実際の動きと違っても、これまでは、その部品を呼ぶアプリを動かすまで分からなかった。

`python -m geas parts ファイル.geas` は、宣言だけを頼りに、引数の範囲の端の値（両端とその隣、0 の周り、真ん中、ビット幅の境目）の全部の組み合わせで、根の言語（Rust）の関数を実際に呼ぶ。見るのは次の 5 つ。

| 見ること | 見つかる誤りの例 |
|---|---|
| いまの toolchain で組めるか | 安定版に無い関数、型の写し間違い |
| panic しないか（デバッグビルドで呼ぶ） | 計算のあふれ、0 で割る、ドキュメントに書いていない panic |
| 戻り値が宣言の範囲に収まるか | 範囲の書き間違い |
| `guarantee` が成り立つか | 保証の向きの書き間違い |
| 2 回呼んで同じ値か | 純粋でない関数 |

標準部品は、さらに**別に書いた手本**（[geas/stdref.py](../geas/stdref.py)：Rust の整数のメソッドを、桁の限りがない Python の整数で書き直したもの）と比べる。248 個を合わせて 33,960 回呼び、全部が合った。手本の無い標準部品があると試験が止まるので、対応表（部品 ↔ 手本）は試験が保つ。

限界：端の値を試すだけなので、証明ではない（間のどこかで外れることは見つけられない）。引数が整数・金額・真偽でない部品は、まだ確かめられない。無限ループとメモリ枯渇は見つけられない。`to_be`・`to_le` は実行環境のバイトの並びで結果が変わる（手本はリトルエンディアン）。

## 3. 足した言語機能

| 機能 | 書き方 | 前はどうだったか |
|---|---|---|
| 負の数・符号の反転 | `-5`、`-x` | 構文エラー（`0 - x` と書く必要があった） |
| 小さいほう・大きいほう・絶対値 | `min(a, b, …)`、`max(a, b, …)`、`abs(x)` | 無かった。範囲に挟む `max(min(x, 99), 0)` が書けず、`if` の文で分けていた |

| 集合に入っているか・写像のキーにあるか | `x in s` | `{ g \| g in s, g == x } is nonempty` と書く必要があった |
| 件数・文字数 | `len(x)`（文字列・集合・写像） | `raw` にだけ使えた。件数は `sum { 1 \| g in s }` |

数のものは、範囲の証明に乗る（`min(m, 99)` は 99 以下、`abs(m)` は 0 以上、`len(名前)` は型の長さまで、と検査が使う）。書き方は、Python・SQL・Rust のどれから来た AI でも同じ意味に読むもの（`in`・`len`・`min`・`max`・`abs`）を選んだ。

## 4. 残っているもの（決めることがある）

一般の言語にあって geas に無いもののうち、書き方に決めることがあるので、手を付けていないもの。

| 順 | 無いもの | いまの書き方 | 決めること |
|---|---|---|---|
| 1 | `if` の中の `let` と `for` | `let` は `if` の前に書く | `if` を抜けたら名前が消える、でよいか（付け直しの禁止とは両立する） |
| 2 | 文字列を定数と比べる | 処理の中では書けない（`rule` の条件では書ける） | 比べる定数が、型の長さ・文字種に合わないときをエラーにするか |
| 3 | 文字列をつなぐ・集合に要素を足す | 書けない（`raw_cat` は `dangerous` の中だけ） | 長さの上限を、足し算で示すか |
| 4 | 2 つの項目を比べる不変条件（`stock <= cap`） | 書けない（検査できない約束は書けない、で止まる） | どの形まで検査するか |
| 5 | `library` の具体例 | 無い | 宣言に `example f(3) == 9` のような行を書かせ、`geas parts` が端の値に足して呼ぶか |

検査の小さな気づき：使っていない `let` に警告が出ない。`library` の境界値の検査の結果（通った・通していない）を、仕様書の「人の保証」に出すと、レビューする人が見分けられる（未着手）。
