## 同時起動（S7）について

- 厳密な同時実行（マルチコアなど）が要るのは、ユースケースではなく機能要件（性能など）の側で出てくると考える。
- 決定済みの方針（2026-10-25）は残す：同時に動かすときは、書き込みの重なりを静的に拒否し、可換な更新（加算、集合への追加、最大・最小）だけ許す。
- 将来の使い道：生成器が処理を並列に実行してよい条件として使う（重ならない、または可換と示せたときだけ並列にしてよい）。実行速度が最優先なので、そのときに実装する。

## 並列起動の書き方（2026-10-26）

同じ結果から複数の処理を起こすときは、`受付 → par { メール通知, プッシュ通知 }` と書く。実行は書いた順で、順序は決まっている。
仕様書（ユースケース図の元）には「並列［メール通知 ＋ プッシュ通知］」と出る。「どれかに行く」分岐（結果の種類ごとの行き先）とは別で、par は全部が起こる。
同じ結果に行き先を続けて書く形（`受付 → A, 受付 → B`）は、分岐と区別がつかないのでエラー。
応答（reply）と待つ（wait）は、いまは par に入れられない（返す前か後か、止まっている間か、の定義が無いため）。待ち合わせ（全部の結果がそろったら次へ）は v0.1.0 の外。

par の枝の規則（2026-10-26 tazyamah の提案、BPMN の並列ゲートウェイに寄せる）：
- 枝どうしでデータを共有しない（各枝は、起こした結果の中身だけを受け取る）。
- 枝の処理は、データを書かない（書き込み・状態の遷移・新規作成はエラー）。読むことと、外部作用の要求だけにする。書き込みは、応答を受ける別の処理（待つ → トリガ → 処理）でやる。これで排他制御を考えなくてよい。
- 将来の緩め方：書く項目が重ならないと静的に示せたら許す（S7 の方針）。厳しい側から始めるので、既存のコードは壊れない。
- 仕様書の図は BPMN に寄せる（par は並列ゲートウェイ、結果ごとの行き先は排他ゲートウェイ）。生成する仕様書に、フローごとの Mermaid の図が出る。

## リクエスト間の排他制御（2026-10-26 tazyamah）

par の枝どうしの排他制御と、Web サービスなどで別々のリクエストの処理どうしが同じデータを触るときの排他制御は、別の話。
後者は、トランザクションの考え方で、言語の文法ではなく生成器（と基盤）が解決する。1つの処理は1つのトランザクションで、各処理は「ほかのリクエストの処理と直列に並べた場合と同じ結果になる」ことを、生成器が守る約束とする。
生成器が使える材料：処理ごとに「読む」「書く」の項目が宣言されていて、検査器が静的に確かめている。

## 名前を半角英数にする方針と、表示名（2026-10-26 tazyamah）

Geas のコードは人が読まず、生成器で別の言語に出すときに日本語の名前が使えない場合があるので、名前（型・entity・項目・処理・状態など）は半角英数にする。
日本語などの表示名は、javadoc / rustdoc と同じ説明コメント（`///`）に書く。`///` の本文は既定の表示名、`@ja …` `@en …` のように言語ごとにも書ける。コンパイルされるコードの意味は変えず、生成する仕様書の「名前と表示名」の表だけに使う。
実装は段階的：(1) 説明コメントの読み取りと、仕様書の表（済）。(2) 組み込みの名前（`round(値, floor|ceil|half_up, JPY)`、`vtime` と `year month day hour minute second`）（済）。(3) お店の例を半角英数に置き換え、仕様書・診断・具体例の突合には表示名を出す（済）。(4) 名前の書き方の検査（済）。(5) 生成する Rust の内部の名前を英語に（未）。(6) 表示名の抜けの検査（未）。

名前の書き方（コマンドは常に検査する。2026-10-26）：
- 使える文字は、先頭が英字で、あとは英数字と `_`。記号（`@` `$` など）は付けない。種類は大文字小文字で見分ける。Rust の慣習（型は UpperCamel、関数と変数は snake_case）と同じなので、生成するときに名前を変えずに使える。
- UpperCamel：論理型・entity・状態とその名前・結果とその種類・外部作用の名前空間・トリガ・フロー・出来事。例 `Order`、`NonNegMoney`、`Received`。
- lower_snake：項目・変数・処理（deed）・問い合わせ・入力・部品・変換（呼ぶと値が返る関数なので）・外部作用の操作と引数。例 `order_id`、`place_order`、`Payment.charge`。
- 仕様書に出る名前（型・項目・状態・結果の種類・処理・問い合わせなど）に表示名（直前の `///`）が無いと、検査器が警告で教える（エラーではない。仕様書には名前のまま出る）。処理の中の変数は仕様書に出ないので数えない。
- 生成する Rust の内部の名前（`Store` `Write` `Effect` `Ctx` `Input` `Output` `Ratio` `check_range` など）と、画面（JS）と受け渡す JSON のキー（`name` `ctx` `input` `store` `result` `args` `body` `effects` など）は英語にした。具体例の突合に使う変化・外部作用の書式（`新規(` `冪等キー=`）は、計画書の書式なので日本語のまま。
- 小文字の名前は、組み込みの型・関数と宣言や文を始める語（`int` `round` `let` など）と同じにできない。大文字で始まる名前は、組み込みとは綴りが重ならない。
