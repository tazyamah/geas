# v0.1.0 の範囲（未決だった項目の扱い）

2026-10-26 時点。人が読むメモで、強制力は検査器にある。

| 項目 | v0.1.0 での扱い |
|---|---|
| 契約違反の policy（S8） | 「示せないとき」は常に厳しい扱い（エラー）だけで出す。緩い／厳しいの切り替えは後回し |
| `while` と終了条件つきの繰り返し（S9） | v0.1.0 の外。繰り返しは、集合の要素ごと（`for … in`）だけ |
| 保存先 `store` と「記録」の状態（S10） | 言語には宣言（`store 名 in 保存先`）と、言語が足す未同期の状態だけを残す。同期の実行は基盤の仕事 |
| 同時起動の書き込みの重なり（S7） | v0.1.0 の外。言語には、厳密に同時に動く道を入れない。複数の後続を並べて書けても、暗黙の処理順（書いた順）で動く前提で、順序は決まっている |

## 同時起動（S7）について

- 厳密な同時実行（マルチコアなど）が要るのは、ユースケースではなく機能要件（性能など）の側で出てくると考える。
- 決定済みの方針（2026-10-25）は残す：同時に動かすときは、書き込みの重なりを静的に拒否し、可換な更新（加算、集合への追加、最大・最小）だけ許す。
- 将来の使い道：生成器が処理を並列に実行してよい条件として使う（重ならない、または可換と示せたときだけ並列にしてよい）。実行速度が最優先なので、そのときに実装する。

## 並列起動の書き方（2026-10-26）

同じ結果から複数の処理を起こすときは、`受付 → par { メール通知, プッシュ通知 }` と書く。実行は書いた順で、順序は決まっている。
仕様書（ユースケース図の元）には「並列［メール通知 ＋ プッシュ通知］」と出る。「どれかに行く」分岐（結果の種類ごとの行き先）とは別で、par は全部が起こる。
同じ結果に行き先を続けて書く形（`受付 → A, 受付 → B`）は、分岐と区別がつかないのでエラー。
応答（reply）と待つ（wait）は、いまは par に入れられない（返す前か後か、止まっている間か、の定義が無いため）。待ち合わせ（全部の結果がそろったら次へ）は、トリガの `all reply` で書く（下の「待ち合わせ」）。

par の枝の規則（2026-10-26 tazyamah の提案、BPMN の並列ゲートウェイに寄せる）：
- 枝どうしでデータを共有しない（各枝は、起こした結果の中身だけを受け取る）。
- 枝の処理はデータを書いてよい（2026-10-27 に緩めた）。ただし、枝どうしで実行する順が結果に効かないことを、静的に確かめる。次のどれかがあるとエラー：
  - 2つの枝が同じ項目に書く（どちらも加算・減算 `+=` `-=` の更新だけなら重なってよい）。
  - ある枝が書く項目を、ほかの枝が読む（読む前か後かで結果が変わる）。
  - ある枝が新規作成するデータを、ほかの枝が触る（採番と読み書きの順が効く）。
  - 2つの枝が同じデータの状態を動かす。
- 順序が効かないので、生成器は枝を並列に実行してよい。いまの生成コードは書いた順に動かす（結果は同じ）。排他制御は、リクエスト間と同じく生成器と基盤の仕事で、言語には書かない。
- 仕様書の図は BPMN に寄せる（par は並列ゲートウェイ、結果ごとの行き先は排他ゲートウェイ）。生成する仕様書に、フローごとの Mermaid の図が出る。

## 待ち合わせ（合流）（2026-10-27 tazyamah）

合流点は2種類で、トリガの行ごとに書き分ける（BPMN の排他の合流と並列の合流）。

```
trigger PaymentPending(order_id: id) {
  all reply PaymentSucceeded, StockReserved → ship_order   // 全部の応答がそろったら進む
  reply PaymentDeclined → handle_declined                   // どれか1つ：先に来たら進む（従来どおり）
  deadline now + 30 min → expire_payment                    // 期限
}
```

- トリガは、どれかの行が先に成り立った時点で解ける。`all` の行は、並べた応答が全部そろったときに成り立つ（順序は問わない。同じ応答が2回来ても1回と数える）。
- 一部が失敗として来たときの扱い（決定）：言語は「失敗」を決めない。そろうまで待ち、受け取る処理が判断する。早く解きたい応答（決済の拒否など）は、`all` を付けない reply の行に書けば、来た時点で進む。
- 期限は必須（従来どおり）。そろわないまま期限が来たら、期限の行き先へ進む。
- 誤りは検査で止める：all の応答が1つだけ・重複、同じ応答が all の行と単独の行の両方にある、同じ応答が複数の all の行にある。
- 行き先の処理の入力は、トリガの引数に、起きた応答の中身を足したもの（次の「応答の中身」）。
- 仕様書には「全部の応答 A ＋ B」と出る。生成する Rust の `TriggerDef` と画面用の定義には、種別 `all` と応答の名前の列が出る（待つこと自体は基盤の仕事）。

## 応答の中身（2026-10-27）

応答は外の部品（人を含む）から返ってくるので、中身は外からの入力と同じ扱い。`reply 名前(中身: 型 [required], …)` を最上位に宣言する（宣言のない応答は、これまでどおり中身なし）。

```
reply PaymentDeclined(reason: id required)
reply PaymentSucceeded(auth_id: id required)
```

- 起きた応答の中身は、トリガの引数に足されて、行き先の処理の入力になる（`all` の行は、並べた全部の応答の中身）。処理の入力は「トリガの引数 ＋ 中身」と名前と型が合わなければエラー（並びは問わない）。
- 中身の名前が、トリガの引数や、同じ行のほかの応答の中身とぶつかるとエラー。
- 受け取るときの確かめ（必須の有無と範囲）は、処理の入力と同じく基盤が境界で行う。宣言は生成する Rust の `replies`（`ReplyDef`）と画面用の定義に出る。仕様書に「応答の中身」の表が出る。
- どのトリガの要因にも使われない宣言は警告。
- `all` で一部が失敗の中身で来たときは、受け取る処理が中身を見て判断する（言語は失敗を決めない）。

## 金額の単位（2026-10-27）

金額 `money(JPY|USD|EUR)` は、単位ごとに別の型として扱う（省くと JPY）。値は最小単位（円・セント）の整数で、単位の違いは検査だけが見る（生成する Rust の値は同じ整数）。

- 違う単位の金額は、足し引きも比較もできない。項目・引数・結果の中身・合成型の成分に入れるときも、単位が合わなければエラー。換算は `convert`・`part` で書く（為替レートは外の部品）。
- 式の単位は、項目・入力・`let` の変数・掛け算・`round`・`sum`・部品の戻り値から追う。`round(値, 方式, 単位)` の単位は、値の金額の単位と同じでなければならない。
- 円以外の金額には、0 以外の数字を直接書けない（100 がセントなのかドルなのか決まらない）。`money(整数, USD)` で最小単位の個数から作る。0 は、どの単位としても書ける。
- **通貨コードを slot などで渡す**（2026-10-27 tazyamah）：組み込みの型 `currency`（JPY・USD・EUR。遷移の無い列挙で、Rust では `Currency`）を、入力・slot・項目・引数に持てる。金額の単位には、同じ並びにある通貨の名前を書ける（`money(currency)`）。
  - `slot currency: currency` と `slot shipping: money(currency)` のように書くと、1回の実行のあいだ単位が1つに決まった金額になり、同じ slot の通貨どうしだけ足し引き・比較できる。固定の円や、別の通貨の金額と混ぜるとエラー。
  - 保存する金額は、通貨の項目と一緒に持つ（`currency: currency required`、`total: money(currency) required`）。読み出した金額は、`if order.currency != currency { return … }` か、集まり全体を `{ k | (k, v) in items, Product[k].currency != currency }` が空と確かめた後で、slot の通貨の金額として扱える。確かめずに混ぜると「別の通貨」でエラー。
  - 外部作用の引数や結果の中身も、`amount: money(currency), currency: currency` と並べて書く。呼ぶ側は、その通貨の引数に渡した値（`order.currency` など）と、金額の単位が合っているかを検査する。
  - 実行時に確かめるのは、外から来る通貨コードが列挙のどれかであることだけ。金額の足し引きごとの確かめは増えない。
- 円とドルの混在の検査は静的で、実行時には何も確かめない（外から来る値の単位は、入力の型で決まっている）。

## 合成型を使える場所（2026-10-27）

合成型（`ltype 住所 { zip: …, line: … }`）は、項目と処理の入力・slot に加えて、結果の中身、外部作用の引数、応答の中身、トリガの引数に書ける。生成する Rust では成分を持つ構造体で、画面・外部とやりとりする JSON には成分が平らな入れ子で出る。問い合わせの入力と部品の引数は、まだ使えない（使う題材が出たら足す）。

## リクエスト間の排他制御（2026-10-26 tazyamah）

par の枝どうしの排他制御と、Web サービスなどで別々のリクエストの処理どうしが同じデータを触るときの排他制御は、別の話。
後者は、トランザクションの考え方で、言語の文法ではなく生成器（と基盤）が解決する。1つの処理は1つのトランザクションで、各処理は「ほかのリクエストの処理と直列に並べた場合と同じ結果になる」ことを、生成器が守る約束とする。
生成器が使える材料：処理ごとに「読む」「書く」の項目が宣言されていて、検査器が静的に確かめている。

## 名前を半角英数にする方針と、表示名（2026-10-26 tazyamah）

Geas のコードは人が読まず、生成器で別の言語に出すときに日本語の名前が使えない場合があるので、名前（型・entity・項目・処理・状態など）は半角英数にする。
日本語などの表示名は、javadoc / rustdoc と同じ説明コメント（`///`）に書く。`///` の本文は既定の表示名、`@ja …` `@en …` のように言語ごとにも書ける。コンパイルされるコードの意味は変えず、生成する仕様書の「名前と表示名」の表だけに使う。
実装は段階的：(1) 説明コメントの読み取りと、仕様書の表（済）。(2) 組み込みの名前（`round(値, floor|ceil|half_up, JPY)`、`vtime` と `year month day hour minute second`）（済）。(3) お店の例を半角英数に置き換え、仕様書・診断・具体例の突合には表示名を出す（済）。(4) 名前の書き方の検査（済）。(5) 生成する Rust の内部の名前を英語に（未）。(6) 表示名の抜けの検査（未）。

名前の書き方（コマンドは常に検査する。2026-10-26）：
- 使える文字は、先頭が英字で、あとは英数字と `_`。記号（`@` `$` など）は付けない。種類は大文字小文字で見分ける。Rust の慣習（型は UpperCamel、関数と変数は snake_case）と同じなので、生成するときに名前を変えずに使える。
- UpperCamel：論理型・entity・状態とその名前・結果とその種類・外部作用の名前空間・トリガ・フロー・出来事。例 `Order`、`NonNegMoney`、`Received`。
- lower_snake：項目・変数・処理（deed）・問い合わせ・入力・部品・変換（呼ぶと値が返る関数なので）・外部作用の操作と引数。例 `order_id`、`place_order`、`Payment.charge`。
- 仕様書に出る名前（型・項目・状態・結果の種類・処理・問い合わせなど）に表示名（直前の `///`）が無いと、検査器が警告で教える（エラーではない。仕様書には名前のまま出る）。処理の中の変数は仕様書に出ないので数えない。
- 生成する Rust の内部の名前（`Store` `Write` `Effect` `Ctx` `Input` `Output` `Ratio` `check_range` など）と、画面（JS）と受け渡す JSON のキー（`name` `ctx` `input` `store` `result` `args` `body` `effects` など）は英語にした。具体例の突合に使う変化・外部作用の書式（`新規(` `冪等キー=`）は、計画書の書式なので日本語のまま。
- 小文字の名前は、組み込みの型・関数と宣言や文を始める語（`int` `round` `let` など）と同じにできない。大文字で始まる名前は、組み込みとは綴りが重ならない。
