# geas の REST の考え方

geas は、外から触れるものすべてに URL を与えます。URL の形は言語が決め、書く人は選べません。ここには、その決まりと理由をまとめます。書き方の細部は [language-reference.md](language-reference.md) の 10 章、サーバーの動きは [server.md](server.md) にあります。

## 1. なぜ形を固めるのか

geas の目標は、人がコードを読まずに仕様書だけでレビューできることです。URL の付け方に自由があると、「この URL は何をするのか」を 1 つずつ読み解くことになります。形を 1 つに固めれば、URL の表を見るだけで、何が増え、何が読まれ、何が変わるのかが分かります。

## 2. 決まり

### リソースは名詞、動作は 5 つ

| 動作 | メソッドと URL | 意味 |
|---|---|---|
| `index` | `GET /orders` | 集まりを読む |
| `show` | `GET /orders/:id` | 1 つを読む |
| `create` | `POST /orders` | 新しく作る |
| `update` | `PUT /orders/:id` | 1 つを置き換える |
| `destroy` | `DELETE /orders/:id` | 1 つを消す |

- これ以外の動作は作れません。例外はありません（`new` と `edit` は、画面の URL にだけ出ます）。
- **PATCH はありません**。一部だけを変えたいときは、その部分を別のリソースに切り出します。
- 状態を進める命令も、名詞のリソースにして `create` します（決済する → `POST /order_settlements`）。注文の下に動詞をぶら下げません。
- 行き先の振り分けが要るなら、別のリソースにします。1 つの動作が呼ぶものは 1 つです。
- 入れ子は、ID を持つ親の子だけです（`/customers/:customer_id/orders`）。

### POST は、URL が増えるときだけ

POST はリソースの作成です。つまり、URL（のような文字列で管理しているもの）が増えるときにだけ使います。検索の条件を POST の本文で渡して、その場で結果を返す口は作りません。読むだけなら GET です。

### リソースは細かく切り、条件の組には名前を付ける

「未払いの注文」「自分の注文」のような決まった絞り込みは、呼ぶ側に条件を渡させず、名前を付けたリソースにします（`GET /unpaid_orders`）。行の集まりには範囲（`scope`）で名前を付け、候補は `.geas` に直に書きます（`where status in [PaymentRequested, Paid]`）。

リソースを細かく切る前提なので、集まりの和や差、呼ぶ側が候補の集まりを選ぶ絞り込みは、ほとんど起きない想定です。言語にも入れていません。

### パスは「どのリソースか」、クエリ文字列は「絞り込みの条件」

- **パス**に載るのは、どのリソースかを決める値だけです。ID、親の ID、1 つのキー（`/product_prices/:jan`）。
- **絞り込みの条件**は、クエリ文字列で渡します。形は `q[名前]=値` だけです。

```
GET /order_searches?q[from_time]=1763251200&q[to_time]=1763337600
```

条件をパスに並べる形（`/orders_in_periods/:from_time/:to_time`）は採りません。URL の仕様を知らないと、どの値が何なのか分からないからです。`q[名前]` なら、名前が URL に出て、順番にも意味がなく、指定しない条件は書かないだけで済みます。

クエリ文字列を並べて書く形（`from_time=…&to_time=…`）も採りません。条件は、必ず 1 つのオブジェクト `q` にまとめます。条件であることが URL の見た目で分かり、条件でないものが紛れ込みません。

サーバーは、次をすべて 400 で断ります。

- 宣言に無い名前（`q[other]=1`）
- `q[名前]` でない形（`from_time=…`、`q=…`、値の無い断片）
- 同じ名前の重複
- 要る条件が無い
- 数の条件が 10 進の数字でない
- 条件を取らない URL に付いたクエリ文字列（処理を呼ぶ URL も含む）

`.geas` に新しい書き方はありません。問い合わせの入力のうち、パスに載らないものが、そのまま条件になります。`required` の入力は必ず要り、そうでない入力は省けます。

```
query order_search {
  input from_time: time required
  input to_time: time
  …
}
resource OrderSearches {
  index order_search        // GET /order_searches?q[from_time]=…&q[to_time?]=…
}
```

URL に載せられる型は、ID・文字列・状態の名前・整数・金額・日時です。整数・金額・日時は、JSON の本文と同じ数を 10 進の数字で書きます。

検索は、検索のためのリソース（`OrderSearches`）にするのが基本です。もとのリソースの `index` に条件を持たせること（`GET /orders?q[status]=Paid`）もできます。

### 結果の種類ごとに、HTTP の状態を決める

`create`／`update`／`destroy` には、処理の結果の種類ごとの状態を必ず書きます（`Received → 201`、`NoSuchProduct → 404`）。漏れは検査で止まります。

### 外から呼べない URL と、呼べる人

流れの途中の処理（返事や期限から進むもの）にも URL はありますが、「内部」です。サーバーは外からの呼び出しに答えません。役割（`actor`）を宣言したアプリでは、外から呼べる動作すべてに、呼べる人（`for 役割`／`for anyone`）を書きます。

## 3. まだ決めていないこと

- **URL に載せられない条件**（長すぎる、ログに残したくない個人の情報）。案は、条件を `POST /order_searches` で保存して URL を増やし（201）、返った URL を GET で読む形です。POST は作成だけ、の決まりと両立します。必要になってから作ります。
- **ページ送りと並び順**を、呼ぶ側が選ぶ口。`q` の外に置く余地は残してあります。
