# geas の REST の考え方

geas は、外から触れるものすべてに URL を与えます。URL の形は言語が決め、書く人は選べません。ここには、その決まりと理由をまとめます。書き方の細部は [language-reference.md](language-reference.md) の 10 章、サーバーの動きは [server.md](server.md) にあります。

## 1. なぜ形を固めるのか

geas の目標は、人がコードを読まずに仕様書だけでレビューできることです。URL の付け方に自由があると、「この URL は何をするのか」を 1 つずつ読み解くことになります。形を 1 つに固めれば、URL の表を見るだけで、何が増え、何が読まれ、何が変わるのかが分かります。

## 2. 決まり

### リソースは名詞、動作は 5 つ

| 動作 | メソッドと URL | 意味 |
|---|---|---|
| `index` | `GET /orders` | 集まりを読む |
| `show` | `GET /orders/:id` | 1 つを読む |
| `create` | `POST /orders` | 新しく作る |
| `update` | `PUT /orders/:id` | 1 つを置き換える |
| `destroy` | `DELETE /orders/:id` | 1 つを消す |

- これ以外の動作は作れません。例外はありません（`new` と `edit` は、画面の URL にだけ出ます）。
- **PATCH はありません**。一部だけを変えたいときは、その部分を別のリソースに切り出します。
- 状態を進める命令も、名詞のリソースにして `create` します（決済する → `POST /order_settlements`）。注文の下に動詞をぶら下げません。
- 行き先の振り分けが要るなら、別のリソースにします。1 つの動作が呼ぶものは 1 つです。
- 入れ子は、ID を持つ親の子だけです（`/customers/:customer_id/orders`）。

### POST は、URL が増えるときだけ（例外は 1 つ）

POST はリソースの作成です。つまり、URL（のような文字列で管理しているもの）が増えるときにだけ使います。読むだけなら GET です。

例外は 1 つだけです。**本来は GET の問い合わせを、事情があって POST で受ける**ことができます。条件を URL に載せられないとき（長すぎる、氏名や電話番号のように URL とログに残したくない）のためのものです。

```
resource CustomerSearches {
  index customer_search for Staff post "氏名と電話番号で探すので、URL とログに残さない"
}
// POST /customer_searches   本文 {"q": {"name": "…", "phone": "…"}}   答えは 200 と結果
```

- 理由は必ず書きます。仕様書に「POST で受ける問い合わせ」の表が出て、例外であることと理由が人の目に見えます。
- 条件は、GET と同じ 1 つのオブジェクト `q` に入れます（本文では JSON のまま。数は数で書きます）。本文に `q` のほかのキーは書けません。
- 条件は保存しません。URL は増えず、答えはその場で返ります。
- 版（ETag）による 304 と、次のページの URL（`next`）は付きません。続きは、答えの `after` を本文の `q.after` に入れて読みます。
- 書けるのは `index` だけで、そのリソースに `create` は書けません（同じ `POST /customer_searches` になるため）。検索のためのリソースを別に作ります。

### リソースは細かく切り、条件の組には名前を付ける

「未払いの注文」「自分の注文」のような決まった絞り込みは、呼ぶ側に条件を渡させず、名前を付けたリソースにします（`GET /unpaid_orders`）。行の集まりには範囲（`scope`）で名前を付け、候補は `.geas` に直に書きます（`where status in [PaymentRequested, Paid]`）。

リソースを細かく切る前提なので、集まりの和や差、呼ぶ側が候補の集まりを選ぶ絞り込みは、ほとんど起きない想定です。言語にも入れていません。

### パスは「どのリソースか」、クエリ文字列は「絞り込みの条件」

- **パス**に載るのは、どのリソースかを決める値だけです。ID、親の ID、1 つのキー（`/product_prices/:jan`）。
- **絞り込みの条件**は、クエリ文字列で渡します。形は `q[名前]=値` だけです。

```
GET /order_searches?q[from_time]=1763251200&q[to_time]=1763337600
```

条件をパスに並べる形（`/orders_in_periods/:from_time/:to_time`）は採りません。URL の仕様を知らないと、どの値が何なのか分からないからです。`q[名前]` なら、名前が URL に出て、順番にも意味がなく、指定しない条件は書かないだけで済みます。

クエリ文字列を並べて書く形（`from_time=…&to_time=…`）も採りません。条件は、必ず 1 つのオブジェクト `q` にまとめます。条件であることが URL の見た目で分かり、条件でないものが紛れ込みません。

サーバーは、次をすべて 400 で断ります。

- 宣言に無い名前（`q[other]=1`）
- `q[名前]` でない形（`from_time=…`、`q=…`、値の無い断片）
- 同じ名前の重複
- 要る条件が無い
- 数の条件が 10 進の数字でない
- 条件を取らない URL に付いたクエリ文字列（処理を呼ぶ URL も含む）

`.geas` に新しい書き方はありません。問い合わせの入力のうち、パスに載らないものが、そのまま条件になります。`required` の入力は必ず要り、そうでない入力は省けます。

```
query order_search {
  input from_time: time required
  input to_time: time
  …
}
resource OrderSearches {
  index order_search        // GET /order_searches?q[from_time]=…&q[to_time?]=…
}
```

URL に載せられる型は、ID・文字列・状態の名前・整数・金額・日時です。整数・金額・日時は、JSON の本文と同じ数を 10 進の数字で書きます。

検索リソースは**論理的なリソース**です。`q` の値は、保存してある行（物理的なリソース）と 1 対 1 ではありません。だから、絞り込みの条件のほか、続きの位置（下の「続きを読む」）のような「どう読むか」も、同じ `q` に入れます。クエリ文字列のオブジェクトは、いつも `q` の 1 つだけです。

検索は、検索のためのリソース（`OrderSearches`）にするのが基本です。もとのリソースの `index` に条件を持たせること（`GET /orders?q[status]=Paid`）もできます。

### 続きを読む：`q[after]`

`page 20` のある問い合わせは、先頭の 20 件を返します。続きがあるときは、答えに次のページの URL（`next`）が入ります。

```
GET /order_searches?q[status]=Paid
→ { "rows": [ …20 件… ], "next": "/order_searches?q[status]=Paid&q[after]=o-0020" }
```

- 呼ぶ側は、`next` をそのまま GET します。`q[after]` の値はサーバーが作る印で、中身を知る必要はありません。最後のページには `next` がありません。
- `.geas` に書くことはありません。`page` のある問い合わせが、自動で `q[after]` を受けます（その問い合わせでは、入力の名前に `after` を使えません）。
- 何ページ目かを数で渡す形（`page=3`）は採りません。読んでいる途中で行が増減すると、同じ行を 2 回読んだり、飛ばしたりするからです。印は「この行の次から」なので、ずれません。
- 印の行が消えていたら 400 です（最初のページから読み直します）。

### 並びを選ぶ：`q[order]`

並びは `.geas` の `order` で決まります。呼ぶ側に選ばせたいときは、選べる並びを並べて書きます。

```
query order_search {
  …
  order created_at desc     // 1 行目が、選ばないときの並び
  order total desc
  order total asc
}
// GET /order_searches?q[order]=total.desc
```

- 値は `項目.向き`（`total.desc`）です。書いた候補のほかは 400 です。
- `order` が 1 行だけの問い合わせでは、選べません（`q[order]` を書くと 400）。
- 仕様書の問い合わせの表に、選べる並びがすべて出ます。次のページの URL（`next`）にも、選んだ並びが残ります。

### 結果の種類ごとに、HTTP の状態を決める

`create`／`update`／`destroy` には、処理の結果の種類ごとの状態を必ず書きます（`Received → 201`、`NoSuchProduct → 404`）。漏れは検査で止まります。

### 書き込みの版の確認：PUT と DELETE は If-Match 必須

読んでから書くまでのあいだに、別の人が同じ行を書き換えていたら、その書き込みは通しません。

- 行には版があります（行の中身から作る値）。一覧の答えでは各行の `_etag`、1 件の読み出し（show）では応答の `ETag`（`"行の版.答えの版"`）で受け取ります。
- PUT と DELETE は、読んだときの版をヘッダ `If-Match` に載せます（`_etag` の値を `"…"` で囲むか、show の `ETag` をそのまま）。載せなければ 428、今の版と違えば 412 で、どちらも処理を走らせません。`*` と弱い検証子（`W/`）は受けません。例外はありません。
- 428 の答えに、今の版は付けません。版は、その行を読めた人だけが持ちます。
- 行が無いときは、処理が「無い」と答えます（結果の種類ごとの状態）。本人の分だけを扱う URL では、無い行にも 412 を返します（他人の行があるかどうかを、答えの違いで教えないため）。
- 書き換えに成功した応答の `ETag` は、書き換えたあとの行の版です。
- POST の命令（`create`）には要りません。状態の遷移の確かめが担います。
- `.geas` には何も書きません。`update`・`destroy` の処理は、ID の入力で 1 行を引く形（`let x = 実体[id] else { … }`）にします（どの行の版を比べるかを、そこから決めます）。仕様書には、URL の表の下に 1 回だけ出ます。
- 生成した画面は、見せている行の版を送ります。412 のときは「ほかで変更されていました」と出して、画面を新しくします。MCP の書き込みのツールは、入力 `if_match` で版を受けます。

### 外から呼べない URL と、呼べる人

流れの途中の処理（返事や期限から進むもの）にも URL はありますが、「内部」です。サーバーは外からの呼び出しに答えません。役割（`actor`）を宣言したアプリでは、外から呼べる動作すべてに、呼べる人（`for 役割`／`for anyone`）を書きます。

## 3. 生成した画面での見え方

画面の一覧（`show 問い合わせ`）は、上の 2 つをそのまま操作にします。書き足すものはありません。

- `page` のある問い合わせの一覧には、続きがあるあいだ「続きを読む」のボタンが出ます。押すと、答えの `next`（POST の問い合わせでは `after`）をたどって次のページを読み、下に足します。最後まで読むとボタンは消えます。
- `order` を 2 行以上書いた問い合わせの一覧には、「並び」を選ぶ欄が出ます。選ぶと、`q[order]` を付けて最初のページから読み直します。
- 定期の引き直しでは、いま見せているページまでを読み直します（読んだ続きが消えることはありません）。
